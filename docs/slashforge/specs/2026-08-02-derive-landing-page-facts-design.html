Design — derive the published version from package.json

Goal: Stop the docs site restating the version and Node floor by hand — in both the places it does so — and add a guard that fails the build if either is written by hand again.

Problem

The site publishes its version from two hardcoded literals, both frozen at 4.0.1 while npm serves 4.3.1 — six releases of drift, live now.

LocationWhat it isReaches
docs/src/layouts/Base.astro:37the site footer every page — Base wraps DocsLayout, which wraps all 22 others
docs/src/pages/index.astro:152the hero fact chips the home page

Measured against the built output: 17 stale version strings across 16 pages.

The investigation that prompted this found only one of them. It grepped index.astro, found the hero, and stopped — so it reported a single line in a single file. The footer went unnoticed until the guard was dry-run against the whole built site. A fix scoped to that report would have corrected the hero and left every page's footer wrong.

The hero also carries Node 18+, which contradicts package.json's engines: ">=16". The README badge renders from that field and says 16+, so two published surfaces disagree — and CI tests only 18, 20 and 22, meaning >=16 is claimed and never exercised. That string is genuinely hero-only.

This is the third hand-restated fact on this site to drift, after "five slash commands" and a meta description that omitted a command. The pattern is the problem.

Approach

Derive both facts once, in a shared module, and import it in both places.

OptionVerdict
A shared src/pkg.ts Chosen. src/nav.ts is the existing precedent for a shared build-time module at src/ root, imported by layouts. One read, one transform, two consumers.
readFileSync in each file's frontmatter Rejected. Works, but duplicates the read and the transform across two files — repeating in the fix the exact habit that caused the bug.
import pkg from '../../package.json' Rejected. The path leaves docs/, and Vite's serving allow-list rejects paths outside the project root — it risks passing the build and failing npm run dev.

Design

docs/src/pkg.ts — the single source:

import { readFileSync } from 'node:fs';

const pkg = JSON.parse(
  readFileSync(new URL('../../package.json', import.meta.url), 'utf8')
);

/** The published version, e.g. "4.3.1". */
export const version: string = pkg.version;

/** The engines floor as a display string: ">=16" -> "16+", ">=18.0.0" -> "18+". */
export const nodeFloor: string =
  `${pkg.engines.node.replace(/[^0-9.]/g, '').split('.')[0]}+`;

Both facts are derived, not just the version. Node 18+ drifted the same way; a corrected literal would only reset the clock.

Base.astro imports version and renders v{version} in the footer. index.astro imports both and renders the hero chips. Neither file computes anything.

The guard, .github/scripts/check-docs-facts.mjs, follows the link and accessible-name checks in structure: ESM, run from docs/ against the built dist/, one ::error file=…:: per finding, non-zero exit. It matches <span>vN.N.N</span> and fails on any that disagrees with package.json. The narrow pattern is deliberate: the changelog page legitimately lists every past release, and a looser match would flag all of them.

CI gains Node 16, so the floor the package claims is the floor CI tests.

This may fail, and that is useful. node --test arrived in Node 16.17 and was experimental until 18. A red test (16) job is evidence that >=16 is a false claim and engines should be raised. Either result settles it with evidence. If it fails, report it and let the user choose — do not quietly drop 16 from the matrix.

Testing

Red before green, against the real site. The guard must report 17 findings across 16 pages before the fix and 0 after. That number is measured, not estimated — it comes from dry-running the guard against the current build.

  • Both surfaces must be checked in the rendered output. The footer on a page that is not the home page, and the hero chips on the home page. Grepping the source is what missed the footer in the first place.
  • npm run dev must still serve the page. The rejected import approach fails exactly there, so a green build alone would not catch it.
  • The existing suite (43 tests), the docs build, the link check and the accessible-name guard must stay green.

Out of scope

  • The 3-step quickstart block and a copy button on the hero's npx slashforge snippet — reasonable suggestions from the same review, but product decisions rather than defects.
  • Raising engines, unless CI proves 16 unsupportable.
  • The MIT chips in the hero and footer. Also literals, but a licence does not change with releases, so they carry no drift risk.
