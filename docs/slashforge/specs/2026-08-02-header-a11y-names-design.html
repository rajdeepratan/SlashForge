Design — accessible names for the header social links

Goal: Give the four header social links an accessible name, and add a CI guard so the same class of bug cannot ship again unnoticed.

Problem

The four social links in docs/src/components/Header.astro are icon-only. Each has no text content, an <svg> marked aria-hidden="true" as its only child, and a title attribute as the sole source of a name.

Every one of those three choices is individually correct. Together they produce a focusable link that exposes no accessible name: title is the last-resort fallback in the accessible-name computation, it is not announced consistently across screen readers, and it never appears at all for keyboard or touch users. A screen reader reaches four links in a row and can distinguish none of them.

The header is a shared component, so this is four violations on every page of the published site, not four in total. Confirmed against the built output and reported by an external audit as "Headings and anchors must have an accessible name".

The second problem is why nobody noticed. The page looks correct, so the defect is invisible in review. The same file already labels its other icon controls properly — aria-label="Search the docs", "Search", "Sections" — which shows this was an oversight rather than a misunderstanding, and that an oversight is exactly what will happen again with the next icon button.

Approach

Two independent pieces: fix the four links, then add a check that would have caught them.

For the guard, three options were weighed.

OptionVerdict
A separate check-docs-a11y.mjs Chosen. Its own name, its own CI step, its own failure message. An accessibility failure reported by something called a link checker is confusing to whoever hits it.
Extend check-docs-links.mjs Rejected. One fewer file, but it conflates two concerns under a name describing only one.
A third-party runner (axe, pa11y) Rejected. Catches far more, but adds a dependency and a headless browser to a repo whose root package has zero dependencies and whose CI runs npm test with no install step. Disproportionate for one rule.

The guard treats title as insufficient. This is deliberately stricter than the specification requires — title is a valid last-resort name source — because accepting it would mean the guard passes on the exact bug it exists to catch.

Design

The fix. Four aria-label attributes in docs/src/components/Header.astro, carrying the new-tab hint since all four links use target="_blank" and browsers do not reliably announce that:

aria-label="GitHub (opens in a new tab)"
aria-label="npm (opens in a new tab)"
aria-label="Sponsor (opens in a new tab)"
aria-label="Buy me a coffee (opens in a new tab)"

aria-hidden="true" stays on the SVGs — the artwork should remain hidden once the link itself is named. title stays too; it is what produces the mouse tooltip, and it is harmless once a stronger name is present.

The guard. .github/scripts/check-docs-a11y.mjs, following check-docs-links.mjs in structure, style and conventions: an ESM script run from docs/ after the build, walking dist/ for .html files.

It flags any <a> or <button> that has all of:

  • an <svg> among its contents,
  • no text content once tags and entities are stripped,
  • no aria-label and no aria-labelledby on the element,
  • no <title> inside the SVG.

Each finding prints a ::error file=docs/<path>:: annotation naming the element and its href so it is locatable, the script prints a page count like its sibling, and it exits 1 if the count is non-zero.

It runs as a step in the existing docs job in .github/workflows/ci.yml, after the link check, so both operate on the same built output.

Testing

Red before green, against reality rather than a fixture. The guard must report exactly 4 findings on the current build — the four known links — before the fix lands, and 0 after. Verified in that order, because a guard that has only ever passed proves nothing about whether it can fail.

Two further checks on the guard itself, since a checker that is wrong in either direction is worse than none:

  • No false positives. The search button, sections toggle and theme toggle already carry names or visible text and must stay unflagged. The sweep that found this bug already confirmed the built output contains exactly four offenders and no others.
  • The rule is the intended one. An element named only by title must still be flagged — that is the case that shipped.

The existing suite (43 tests), the docs build, and the link check must all stay green.

Out of scope

  • The other three categories in the audit report. Only the accessibility findings are in scope, and within those only the missing-name rule.
  • Broader accessibility auditing — colour contrast, focus order, landmark structure. Worth doing, but a different piece of work with a different shape.
  • The search, sections and theme controls, which are already named correctly.
  • Changing target="_blank" itself. Whether these links should open a new tab at all is a product decision, not an accessibility fix.
