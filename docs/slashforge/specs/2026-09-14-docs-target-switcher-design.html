Design — per-target command names in the docs

Goal: a reader picks Claude Code, Cursor or Codex once, and every command name on the docs site — in code blocks and in sentences — shows the form that actually works in their tool.

Problem

The same command is spelled three ways. /slashforge:code on Claude Code, /slashforge-code on Cursor, $slashforge-code on Codex. The docs show only the first, in 187 places across 14 pages.

A Cursor user reading the install guide is told to type a command that does not exist in their tool. Today the only mitigation is a hand-written :::note on a few pages explaining the difference in prose — which scales badly, is easy to forget on a new page, and still leaves the wrong name as the thing the reader copies.

The naming difference is not the only divergence, but it is the one that appears everywhere. /slashforge:parallel also behaves differently per target — concurrent subagents on Claude Code, sequential with clean context per task elsewhere — and /slashforge:setup does not exist on Cursor or Codex at all. Those are prose problems; this design handles the naming.

Approach

Chosen: derive all three forms from one authored source, mark them at build time, and swap them client-side from a single stored preference. The author writes the Claude Code form once, as today. A rehype plugin finds command references in both fenced blocks and inline <code> spans and tags them with the bare command name. A small script rewrites every tagged node when the reader picks a target.

Two controls drive it, kept in sync: a tab strip in each command block's existing bar — the pattern the user cited from MUI's JS/TS toggle — and a persistent switcher in the site header, so the seven pages that mention commands but contain no code block still have something to click.

TargetFormDerivation from the authored name
Claude Code/slashforge:codeas authored
Cursor/slashforge-code: becomes -
Codex$slashforge-codesame, and / becomes $

Deriving rather than authoring three times is the whole point: 187 references written out per target is 561 strings to keep in sync, and they would drift the first time a command is renamed. This mirrors toSkillCommandRefs at bin/install.js:253, which already does exactly this transformation when installing to the agents target — the docs and the installer end up applying the same rule.

Two alternatives were rejected:

  • Separate URL trees per target (/slashforge/cursor/…). Explicit and works without JavaScript, but triples the built pages, splits every inbound link and search result three ways, and means a reader who switches loses their place.
  • A chooser gate on Get Started and the nav, the first shape discussed. Blocking content behind "which tool?" penalises the common case — someone arriving on a deep link from a search result — and a reader who does not yet know the answer cannot proceed. The header control gives the same power without the wall.

Design

1. Detection is narrow on purpose. The plugin matches /slashforge:<name> where <name> is one of the thirteen known commands, read from a shared list rather than a loose pattern. Anything else — prose about namespaces, a URL containing the string, a changelog entry — is left alone. Every command-bearing fence in the site is plaintext (14 of 14, verified), so Shiki emits one text node per line and the rewrite does not have to reach inside syntax-highlight tokens.

2. What the plugin emits. A matched reference becomes <span data-cmd="code">/slashforge:code</span>. The element ships with the Claude Code form already rendered, so the page is correct before any script runs and correct if scripts never run. A block containing at least one match gets data-has-cmd on its .code wrapper, which is what tells the frame to render tabs instead of the language label.

3. The block tab strip. rehype-code-frame.mjs (src/plugins/rehype-code-frame.mjs, 57 lines) already builds the bar with a language label on the left and Copy on the right. On a block with data-has-cmd the label slot becomes a three-button role="tablist"; every other block keeps its label exactly as now. Copy is untouched, and copies whatever form is currently shown.

4. The header switcher. A compact control in .hdr__right in src/components/Header.astro:41, alongside the existing search button and social links. It is the only control on the seven block-less pages, and the discoverable entry point everywhere else. On narrow viewports it collapses to the active target's short label to avoid crowding the header, which is already a three-column grid.

5. State. One value — claude, cursor or agents-style key — in localStorage under slashforge:target, read on load and written on change. Every read and write is wrapped, because a private window or blocked site data makes the accessor itself throw; on failure the page simply stays on Claude Code for that visit. Selection applies across pages, so a reader sets it once.

6. /slashforge:setup is deliberately not switched yet. It has no Cursor or Codex form — the command does not exist there — so deriving one would print a command that fails. Until that page is dealt with, setup is excluded from the known-command list, which means every reference to it stays in Claude Code form on every target. That is wrong in a small way and visibly so, which is better than wrong in a way that looks right.

7. changelog.md is excluded entirely. It is generated from CHANGELOG.md and is a historical record; rewriting /slashforge:code inside a v4.0.0 entry would misstate what shipped. It holds 22 references, the largest single concentration, which is exactly why it needs saying out loud.

8. Search is indexed in one form, and that is accepted. Pagefind indexes the built HTML, so it sees the Claude Code spelling. A reader searching the literal string slashforge-code will still match on the tokens slashforge and code, so results are found; the excerpt may show a spelling their target does not use. Emitting hidden alternate spellings purely for the index would pollute copy-to-clipboard and screen-reader output for a marginal gain.

Testing

Unit — the derivation. Each of the thirteen commands maps to the three expected forms; an unknown name is left untouched; setup is not in the switchable set.

Build — the plugin marks the right things. Against the real content: every command-bearing fence gets data-has-cmd; no fence without a command gets it; the inline count matches the known reference count per page; changelog.md is untouched; no setup reference is marked.

The regression guard that matters: the default output does not change. With no script running, the rendered HTML text must read exactly as it does today — the Claude Code form everywhere. This is the assertion that proves the change is additive for existing readers and for anyone with JavaScript disabled.

Accessibility. The existing check-docs-a11y.mjs already asserts every interactive element has an accessible name, and the new tabs and header control must pass it unmodified. Beyond that: the tablist is keyboard-operable with arrow keys, the selected tab carries aria-selected, and the control is reachable in tab order.

Existing checks stay green: check-docs-links.mjs, check-docs-facts.mjs, the docs build, and the root npm test suite.

Out of scope

  • The /slashforge:setup page and how it presents a command that does not exist on two of the three targets — parked by agreement, to be handled next
  • Per-target prose beyond command names — notably that /slashforge:parallel runs sequentially on Cursor and Codex, and that Plan mode and /init are Claude Code features. Those need writing, not switching
  • Varying the sidebar, the reading order, or which pages exist per target
  • Any change to what the installer writes, to command names themselves, or to the on-disk template layout
  • The nine discipline-skill pages, which are separate authoring work that will use this mechanism once it exists
