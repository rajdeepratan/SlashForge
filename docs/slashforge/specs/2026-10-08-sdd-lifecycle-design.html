Design — SlashForge SDD Lifecycle

Goal: Turn SlashForge from a plan-driven flow into a spec-driven one — give every repo a persistent Markdown spec home (constitution, architecture, status) and a propose → apply → archive change lifecycle folded into the existing four commands, with no new commands and cross-agent parity (Claude Code, Cursor, Codex) preserved automatically.

Problem

SlashForge is plan-driven, not spec-driven. Its design spec (docs/slashforge/specs/<date>-<topic>-design.html) and plan (docs/slashforge/plans/<date>-<feature>.html) are one-shot, dated HTML documents scoped to a single change. Once the change ships they are never revisited, never reconciled, and never act as an authoritative description of how the system is meant to behave. Nothing in the flow answers "what is this project, what are its non-negotiables, and what is in flight right now" without reading code and git history.

The references the user cited make specs the durable centre of the work: spec-kit uses a constitution plus a specify → plan → tasks → implement → converge cycle; openspec keeps specs as the source of truth through a propose → apply → archive lifecycle. SlashForge has the phases of this (brainstorm, plan, verify, review) but none of the persistence: no constitution, no living project docs, no change folder that survives the change, no convergence against a spec, and no archive step.

Approach

Chosen: introduce a persistent, Markdown spec home under docs/slashforge/ and fold a propose → apply → archive lifecycle into the existing /slashforge-code phases. No new commands: the brainstorm phase proposes a change, implementation applies it, and post-merge cleanup archives it. Because the whole surface is files the agent already reads and writes, parity across Claude Code, Cursor and Codex is automatic.

Alternatives rejected:

  • Dedicated spec commands (/slashforge-propose, /slashforge-apply, /slashforge-archive), mirroring the references. Most discoverable, but breaks SlashForge's "four commands, same name everywhere" identity and triples the install/render surface across three agents. Rejected.
  • Reconciled capability specs (openspec's model: one current spec per capability, updated on archive). Truer to SDD, but the user chose the simpler feature-folder archive where a completed change moves to archive/ unchanged. Rejected by decision.
  • Keep HTML for specs/plans. Living source-of-truth docs must diff cleanly, grep, and review in PRs; HTML via the shared shell does none of these. Rejected for the persistent docs (investigation reports stay HTML — they are read-only artefacts, not living specs).

Design — spec home layout

All paths are Markdown under the existing docs/slashforge/ namespace, so they coexist with the user's own docs/ and never collide.

docs/slashforge/
├─ constitution.md     # non-negotiables (human-authored; .claude/rules/ reference it)
├─ architecture.md     # tech stack, standards, design patterns
├─ status.md           # what is active now + recently archived
├─ active/             # changes currently being built
│  └─ <change-slug>/
│     ├─ requirements.md   # WHAT & WHY (product scope)
│     ├─ plan.md           # HOW (files changed, schemas, approach)
│     └─ tasks.md          # sequential checklist, - [ ] / - [x]
└─ archive/            # completed changes, moved here unchanged on merge
   └─ <change-slug>/

Constitution vs. existing rules. SlashForge setup already generates .claude/rules/ and CLAUDE.md. constitution.md becomes the single human-authored home for non-negotiables; the generated rules reference it rather than restate it, so there is one source and no drift.

Design — phase mapping in /slashforge-code

The lifecycle is not bolted on; it is the existing phases, re-pointed at the new files. The four mandatory user gates are unchanged.

PhaseTodayBecomes
1 — Intake / brainstormdesign .html in specs/writes active/<change>/requirements.md (propose)
2 — Planplan .html in plans/writes active/<change>/plan.md + tasks.md
5 — Implementimplement to planwork through tasks.md, flipping - [ ] to - [x] (apply)
6 — Verifylint / test / buildsame, plus converge: verify implementation against requirements.md; every task box must be checked
7 — Reviewmatches the planmatches requirements.md and constitution.md
10 — Post-merge cleanupbranch cleanupsame, plus archive: move active/<change>/ → archive/<change>/ and update status.md

The change slug is a short kebab name chosen at intake (e.g. sdd-lifecycle). If a slug already exists in active/ or archive/, the intake phase appends a numeric suffix rather than overwrite.

Design — setup scaffolding

/slashforge-setup scaffolds the tree and generates the three top-level docs from its existing codebase exploration: architecture.md (detected stack, test/build commands, conventions), a starter constitution.md (confirmed with the user), and an initial status.md. active/ and archive/ start empty. This works for existing repos — nothing requires a greenfield start, and no code specs are back-filled.

Design — format and quick mode

tasks.md uses GitHub-style Markdown checkboxes (- [ ] → - [x]), replacing the HTML ☐/☑ mechanism; the slashforge-splice.js shell is no longer used for specs or plans (it stays for investigation reports). /slashforge-code -quick writes a lean plan.md and tasks.md and skips requirements.md, matching today's lean behaviour. /slashforge-investigate is unchanged.

Design — files touched

Source of truth is templates/ (installed copies in ~/.claude/setup/slashforge/ are generated). Expected edits: templates/slashforge/brainstorm.md, plan.md, setup.md, verify.md, request-review.md; templates/slashforge-workflow.md, slashforge-workflow-quick.md, and the setup-generators that emit constitution.md/architecture.md/status.md; the claude-render and other render fixtures/tests that assert HTML specs/plans; the docs site under docs/src/content/; and CHANGELOG.md. No package.json version bump (per the user's standing "no new version" instruction).

Testing

Unit/fixture: update the render tests that currently assert design/plan HTML so they assert the new Markdown artefacts (or drop the HTML path for these two types). Add a fixture asserting setup scaffolds the docs/slashforge/ tree with the three top-level files. Add a test that the archive step moves a change folder from active/ to archive/ and updates status.md. Cross-agent: confirm the Claude/Cursor/Codex renders of the edited guide files all describe the identical lifecycle (existing parity tests extended). End-to-end (manual, per slashforge-verify): run /slashforge-code on a throwaway change and confirm the folder is created at intake, filled through plan, checked off in implement, and archived post-merge. Whole suite green via npm test before any PR.

Out of scope

  • Reconciled per-capability specs / an openspec validate-style linter (the "full parity" option the user declined).
  • New standalone commands of any kind.
  • Back-filling specs for existing code beyond the generated architecture.md.
  • Converting investigation reports away from HTML.
  • Any package.json version bump or release.
