Design — One install for Claude Code, Cursor and Codex

Goal: npx slashforge, with no --target, sets SlashForge up for Claude Code, Cursor and Codex in one go. Each host works without the user choosing anything, and nothing one host needs can overwrite what another needs.

Problem

PR #58 adds Cursor and Codex through a --target flag. That has two faults:

  • It makes the user choose. The user has to pick a host at install time, even though they may use several.
  • Cursor and Codex overwrite each other. Both targets install to the same ~/.agents/ folders but render different content. Installing one silently replaced the other until the guard in b9d8462 made the switch refuse.

The owner's requirement: one install, and it just works in whichever host the user opens.

Decisions

QuestionDecision
Install mechanismnpx slashforge (and --project) as today; no postinstall script.
Which hostsAlways all three, whether or not a host is installed on the machine.
Serving Cursor and Codex from shared ~/.agents/Approach A: one host-neutral skill set plus per-host guide folders, chosen at runtime.

Constraints from the hosts

  • Codex reads user-level skills only from ~/.agents/skills; its other locations are an admin folder (/etc/codex/skills) and its built-in skills. Duplicate skill names are all listed in its selector (Codex skills docs).
  • Cursor reads ~/.agents/skills and ~/.cursor/skills, plus ~/.claude/skills and ~/.codex/skills for backward compatibility (Cursor skills docs).
  • Consequence: anything Codex can see, Cursor also sees. A separate copy per host would show every command twice in Cursor, so one skill set has to serve both.
  • Claude Code commands live in ~/.claude/commands/, which neither Cursor nor Codex reads, so they stay independent.

Install layout

ForPathContents
Claude Code~/.claude/commands/slashforge/, ~/.claude/setup/slashforge/Unchanged from 4.5.0: /slashforge:* commands and skills, guides, assets, meta.json.
Cursor + Codex~/.agents/skills/slashforge-*/SKILL.mdOne host-neutral skill set, all 13 entry points and skills, setup included.
Cursor~/.agents/setup/slashforge/cursor/Guides rendered for Cursor, plus its own copy of the four assets.
Codex~/.agents/setup/slashforge/codex/Guides rendered for Codex, plus its own copy of the four assets.
Both~/.agents/setup/slashforge/meta.jsonVersion, install time, mode, and the host folders written.

--project writes the same tree under ./.claude/ and ./.agents/, with repo-relative paths as today.

The four assets are forge-report-shell.html, forge-open.sh, forge-splice.js and forge-review-payload.js. Copying them into each host folder keeps every guide's paths inside its own folder.

Rendering

  • Claude render: blocks [claude], into ~/.claude/. The output must be byte-identical to 4.5.0.
  • Guide renders: blocks [agents, cursor] into cursor/, and [agents, codex] into codex/. {{INSTALL_PATH}} is the concrete host folder.
  • Skill render: blocks [agents] only, rendered once.
    • {{INSTALL_PATH}} becomes <root>/<host>, with <host> left in literally.
    • Command references are rewritten to the Cursor form, /slashforge-name.
    • The frontmatter name becomes slashforge-name.
    • A skill template may not contain cursor, codex or neutral blocks. The validator rejects them.
  • setup.md: its 30 host-specific passages move into a new per-host guide, forge-setup-flow.md, and setup.md becomes a dispatcher that reads it. That's the shape code.md already has with forge-workflow.md. Claude's setup.md keeps its content inline and renders byte-identical. forge-setup-flow.md is installed only in the cursor/ and codex/ folders, never for Claude.
  • investigate.md, review-pr.md, request-review.md: each has two host passages. These move into their workflow guides, or become neutral wording where the difference is only a name.
  • The agents target is removed. The neutral block name goes with it: its content is dropped, or promoted into the skill render where it is truly host-neutral.

Skill preamble

Every rendered skill begins, right after its frontmatter, with:

You are running in Cursor or in Codex. In every path below, replace <host> with
cursor or codex to match. Commands are written /slashforge-name; in Codex invoke
them as $slashforge-name. If you cannot tell which host you are in: a .codex/
folder in the repo means Codex and a .cursor/ folder means Cursor; if neither
or both, ask the user once and use that answer for the rest of the session.

Why this is acceptable: the model's only runtime judgement is naming its own host, which each host states in its system prompt. Everything host-specific is still rendered deterministically at install time.

CLI

  • npx slashforge installs both locations. --project, --dry-run and --yes behave as today.
  • --target and --target=… exit 1 with: "--target is no longer needed: one install sets up Claude Code, Cursor and Codex."
  • Removed: the vendor-switch guard (otherTargetInstalled), TARGET_ALIASES and the target-specific closing messages.
  • Closing message lists both locations and the three invocation forms: /slashforge:code, /slashforge-code and $slashforge-code.
  • status reports both locations: version, guide counts per host folder, and commands. A location that's missing or older is called out, with a suggestion to re-run npx slashforge.
  • uninstall removes both locations, with the same safety as #88: only kit files, only slashforge-* folders in the shared skills directory, and --yes required without a terminal.
  • Shadowing notes: the global-install warning stays for Claude Code. For --project with a global install also present, a note says Cursor and Codex may list both copies.

Failure handling

  • All or nothing on templates: every template is validated for all three renders before any file is written, so a broken package installs nothing.
  • Write failures: the two locations are installed one after the other. If one fails, the error names it, the other is left as written, and the exit code is non-zero. Re-running is safe because installs are repeatable.
  • Dry run: --dry-run lists both locations from plannedWrites, the same list the install uses.

Upgrades

No user has a Cursor or Codex install, because #58 never shipped. A 4.5.0 install is only ~/.claude/, which upgrading leaves identical and alongside which it adds ~/.agents/. No migration is needed.

Testing

  • Dry run and install: plannedWrites and installFiles list the same files in both directions, globally and with --project. A CLI test checks the dry run against the files on disk.
  • Claude render: byte-identical to 4.5.0, compared against templates rendered from tag v4.5.0.
  • Skill render:
    • no cursor or codex block survives
    • the preamble is present
    • every <root>/<host>/… path exists on disk for both cursor and codex
    • no /slashforge: colon form remains
  • Per-host guides keep the existing checks: Cursor's hooks schema, Codex TOML subagents, .mdc rules, and so on.
  • CLI:
    • --target is rejected
    • status and uninstall cover both locations
    • user files survive uninstall in both
    • the no-TTY uninstall refusal and flag-free CI updates still work
  • Docs: the build and the links, targets, a11y and facts checks pass. The docs-targets check keeps the command-form switcher.

Manual verification before merge

This needs the real apps, so the owner runs it:

  1. On a clean machine or a fresh HOME, run npx slashforge from the branch build.
  2. Claude Code: /slashforge:code is listed and reads ~/.claude/setup/slashforge/.
  3. Cursor: each command appears once as /slashforge-code. Running it reads guides from …/cursor/.
  4. Codex: $slashforge-code is available. Running it reads guides from …/codex/. This retires the "not yet verified" note.
  5. Setup in each vendor host: setup in a scratch repo writes Cursor's .mdc rules and hooks.json in Cursor, and Codex's nested AGENTS.md and TOML subagents in Codex.

Documentation

  • README, installation guide, CLI reference: remove every --target mention and describe one command for three hosts.
  • Docs site: the command-form switcher stays; it's about how commands are typed, not how the kit is installed.
  • CHANGELOG: an Unreleased entry for Cursor and Codex support.
  • package.json: the description names all three hosts.

Scope

  • Where the work goes: it continues on feat/cursor-codex-targets (PR #58), which is not merged until the owner says so.
  • Reused from #58: the per-host template sections, the hooks-guide fix and the docs command-form switcher.
  • Out of scope, tracked separately: inline or CRLF marker validation, the toSkillFrontmatter trailing-space check, the root KT/QA notes, and unrelated committed specs and plans.

Risks

  • The model misidentifies its host. Mitigated by the repo-marker fallback and the ask-once rule. The manual checks in both apps confirm the common case.
  • Longer skills. The preamble adds about 60 words to every skill, and every skill pays that cost once per invocation.
  • Duplicate listings in a project that's also installed globally. Codex lists both copies. The --project note tells the user, and recommends one install mode per team as the README already does for Claude Code.
